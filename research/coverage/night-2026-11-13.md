### What `bg3_pause` honestly is

The game has no pause a mod can press. It is the engine's own time scale
(`ls::GlobalSwitches::DeltaTimeScale`) at its floor of 0.001 — one real second buys one millisecond.
Frozen for every practical purpose, not mathematically stopped; the frame loop still runs, so the
bridge still answers; sound does not slow with it. Both the code and the tool's description say so,
because an agent that believes it has a true pause will write a finding that depends on one.

### The batch comparison, ported while the first runs played (`b37394e`)

`bg3_verify`: the "mapped" stage of `check.py`, and the only thing that moves a type out of "seen
alive" into "verified live". It turned out to need much less of `generate.py` than it looked,
because the comparison only ever asks a field type for its width. A type it cannot read is **not
compared** rather than silently passed.

One thing the Python never had to think about: entity handles run past 2^53 (`72057598332905975`
is an ordinary one), so integers are read out of JSON as 64-bit and never through a double, which
would round two different handles into the same number and call a wrong layout right.

Checked on the Nautiloid: `ls::` gave 9 agreed and 0 disagreed on the server, 65 and 0 on the
client; `eoc::item` 3, `esv::inventory` 8. **Every one of them was a type `check.py` had already
recorded as verified** — which is the cross-check that this reads memory the way the Python did.
Nothing new was recorded, and that is the measure itself: the 1,127 unverified types are
unverified because nothing on an idle level carries them. **That count falls only when a run
stages the situation that creates one**, which is the clearest argument yet for runs over tours.

### Python that should be deleted rather than ported

- **`tour.py`, `tours/*.json`, `situations.py`** — tours were the old method, and this design turns
  them from the input into the output. Nothing should generate a tour again; the recorded recipes
  replace them. The `tours/*.json` files are still read by `seen.py context` to explain old
  sightings, so they are data to keep, not code to port.
- **`clean_stand.py`** — exists only to drive the old Python stand. The C# stand's `--instance`
  does the whole job.
- **`graphics_bench.py`, `levels_survey.py`, `dialog_plan.py`** — one-off measurements whose answers
  are already written down (`levels.json`, `plan.md`). Nothing has needed them in weeks.
- **`macos_*.py`, `compare_macos.py`, `fieldmeta_check.py`** — they need `se-fork/reference/`, which
  this repository deliberately does not have.

**`wiki.py` and `todo.py` stay Python.** `todo.py` is now also C# (the tool needed it in-process),
but the script is a fair second reader of the same files and costs nothing to keep. `wiki.py` is

## 5. The blind spot, and what the coverage number is really counting

### The loop can only see ECS components

The ledger counts components. The standing capture notices components. `bg3_probe` dumps component
memory, `bg3_probe_watch` watches component memory, `bg3_verify` checks component layouts - every
one of them reaches instances through `Ext.Debug.GetComponentHolders`. **Everything the engine
keeps outside the ECS is invisible to all of it**, and the ledger cannot report that, because the
ledger counts component types and what is missing is not a component type.

The sound session put numbers on it, unprompted: `Symbols.h` carries **28** engine globals of the
`Type** ls__thing` kind - the string table, the path roots, the client and the server, cursor
control, the drag-drop manager, the translated-string repository and key manager, two game-state
event managers, and `ls__GlobalSwitches` among them. **Four** reach Lua by a getter at all
(`GetGlobalSwitches`, `GetCommandLineParams`, `GetDialogManager`, `GetGameState`).
`ls::GlobalSwitches` by itself is **0x15B8 bytes, most of it unmapped**.

The sharpest illustration arrived by accident. That session offered, as a favour, a reliably
moving engine field to test `bg3_probe_watch` against: with mute-when-unfocused on and the window
behind another, `MasterVolume` and `CutsceneVolume` read "configured 100, in effect 0" while the
other ten are untouched, reproducibly and with no setup. Exactly the test I wanted, having never
got a positive diff on an idle level. **And `bg3_probe_watch` cannot watch it**, because it takes
a component name. The one reliably moving field on this machine is precisely the one the tool
cannot see.

**The fix is the front door, not the bridge**, and both sessions reached that independently:
`Ext.Debug.ReadMemory` already reads anything. What is missing is a way to say *where* without
naming a component - an address and a size, the address being `Ext.Debug.GetModuleInfo().Base`
plus the global's RVA. Their note has how to find such an RVA by byte-pattern scan when the
Toolkit does not hand it over.

### Bringing those systems into the coverage number (the owner's question)

Yes, and it is worth doing - but it changes what the number means, and that is the part to decide
knowingly.

**The denominator is already enumerable offline.** The 28 globals are in `Symbols.h`, and
`symbols.sqlite` holds the Toolkit's exported classes with their layouts, so the list and the size
of each can be built with no game running - exactly as `coverage.json` is built from the ECS
registry today.

**But the unit cannot be the same.** A component type is counted by *sightings*: has anything ever
carried it. A global is always there, exactly once, from the moment the process starts - "seen
alive" is meaningless for it. What is meaningful is **how much of it is named**: declared fields
over total bytes. `ls::GlobalSwitches` is one entry either way, and one entry of 5,560 bytes that
is mostly unknown is not the same fact as one entry of 12 bytes that is fully understood.

**So: two registers, not one blended percentage.** 28 globals folded into 2,647 component types
would vanish - one percent of the count, and some of the largest unmapped surfaces in the engine.
A single number would hide exactly what we just discovered. Two honest numbers, with a headline
that names both, beats one that averages them.

**And this is the uncomfortable part.** The same measure that lets globals in - *named bytes over
total bytes* - applies to components too, and it would deflate the current figure sharply. Today a
component counts as `mapped` whether three of its forty fields are named or all forty are. "2,507
of 2,647 mapped" reads as though 95 % of the engine is understood. It is not: it means 95 % of
component types have **a declaration**, which is a much weaker claim than it sounds, and
`field_8`, `field_9` and `_Pad` are everywhere in the layouts. Byte-level coverage is computable
exactly for our own layout files (offsets and sizes are right there); for the types Script
Extender's author declared it would mean reading the fork's headers, which `generate.py` already
does in part.

My recommendation: build the globals register first, since it is small, offline and purely
additive, and report it beside the component count rather than inside it. Then decide separately
whether to re-cut the component number by bytes - that one is not a tooling change but a change to
what we have been telling people, and it should be the owner's call, made deliberately, not a
side-effect of adding globals.

number as a decision for the owner with no deadline. **They argue the deadline is publication** -
today changing what we say about ourselves costs nothing, and after publication it is a correction
downwards to a number somebody has already quoted, paid for in trust we do not have yet.

And they would remove the single headline percentage rather than recompute it, leaving four plain
numbers for the reader to weigh: component types seen alive of those registered; types with a
declaration of those seen; fields named of those known, in the layouts we wrote; globals reached of
those the symbols list. Four honest numbers read as unfinished work, which is what GateKit is; one
rounded percentage reads as a finished claim, which it is not.

Written up by them as `docs/design/coverage-measure.md`, status "recommendation, not decision",
because it is the owner's call. **I agree with it**, including the deadline, and it does not
conflict with anything in `registers.md` - that file already carries no overall percentage.
